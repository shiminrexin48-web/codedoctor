# CodeDoctor 架构

## 目标

CodeDoctor 对陌生项目执行本地优先的项目识别、静态分析、解释性评分和报告生成。基础扫描必须在没有网络和模型的情况下工作；AI 只负责解释已有证据，不能悄悄改变规则结论。

## 数据流

```text
项目文件
  -> 文件范围与角色分类
  -> 技术栈/用途识别
  -> 适用分析器
  -> 标准化 Finding
  -> 固定权重评分
  -> 网页视图或 JSON/Markdown 报告
  -> 可选 AI 解释
```

## 运行入口

### CLI

CLI 可以直接访问本地文件系统，适合大型仓库。`packages/detectors` 建立 `ProjectContext`，`packages/core` 调度分析器，`packages/scoring` 评分，`packages/report` 写入报告。

### 浏览器

浏览器只读取用户在文件选择器中明确授权的文件。扫描优先在 Worker 中执行，Worker 不可用时才回退主线程。浏览器实现目前包含部分独立规则以避免把 Node 文件系统依赖打进前端，这是已知的重复维护成本；规则变化必须用两端测试防止语义漂移。

## 核心协议

- `Finding`：单条问题、证据、置信度、适用范围和修复建议。
- `AnalyzerResult`：分析器运行、跳过状态和 Finding 集合。
- `ProjectProfile`：项目用途、识别置信度和评分资格。
- `ScoreReport`：维度分、权重、贡献、验证状态和覆盖边界。
- `CodeDoctorReport`：可持久化、可导入的完整报告协议。

跨包协议位于 `packages/shared`。协议变化必须兼容旧报告，或明确提升报告版本并提供迁移策略。

## 信任边界

- 导入项目、报告和扫描证据全部视为不可信输入。
- 不执行被扫描项目的脚本、安装命令或构建命令，除非未来引入独立、显式授权的沙箱执行层。
- 报告渲染不得把项目内容作为 HTML 直接执行。
- AI 请求只发送完成当前解释所需的最小证据，并受数量和输入预算限制。
- `100` 分只表示已运行规则未发现扣分项，不表示安全、正确或可运行。

## 扩展分析器

分析器应先声明能力，再根据 `ProjectContext` 决定是否运行。规则应优先使用结构化清单或语法证据；文本模式必须提供反误报测试。测试、夹具、文档、生成物和依赖目录不能默认按生产源码扣分。

## 已知架构债务

- `apps/web/src/clientScanner.ts` 同时承担文件读取、识别、分析和评分，需逐步拆成 Worker 协议、项目模型和分析器注册表。
- `apps/web/src/App.tsx` 仍包含较多跨视图状态，需拆为视图组件与工作台状态 Hook。
- 浏览器和 CLI 分析规则存在重复实现，应逐步提取为无 Node 依赖的共享规则内核。
- 当前构建运行维度主要基于静态证据，尚无受控执行验证层。
